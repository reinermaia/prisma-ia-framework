SR-001 Protocolo Criptográfico de Validação de Coleta de Mercadoria (Anti-Furto no Balcão)
Alta MVP (Sprint 1)
ASVS: V2.1 (Nível 2 - Verification of Authentication) • OWASP: A07:2021 • ISO 27001: A.9.4.2 (Secure Log-on Procedures) • LGPD: Art. 46 (Segurança da Operação) • Ameaça: THREAT-XF-01
História de Usuário Ágil (INVEST): "Como Expedidor da Cozinha, Quero exigir do entregador um código numérico de retirada de 4 dígitos validado instantaneamente, Para liberar a sacola lacrada apenas ao motoboy legítimo sem atrasar a fila do balcão."
Especificação Normativa (SHALL / MUST): O sistema DEVE (SHALL) gerar um token OTP numérico de 4 dígitos (0000-9999) gerado por algoritmo criptograficamente seguro (CSPRNG) associado univocamente ao pedido pago. O terminal KDS do restaurante NÃO DEVE transicionar o pedido para 'Em Transporte' sem a correspondente validação bem-sucedida do token. O sistema DEVE bloquear novas tentativas e acionar alarme preventivo após 3 submissões incorretas consecutivas.
🛠️ Passos Práticos de Implementação para a Fábrica de Software:
  • 1. Gerar token usando CSPRNG ('secrets' no Python ou 'crypto.randomInt' no Node.js) no momento em que o pagamento for confirmado.
  • 2. Persistir o hash do OTP no Cache Redis com TTL de expiração de 45 minutos (tempo máximo regulamentar de expedição).
  • 3. Criar endpoint POST /api/v1/kds/orders/{order_id}/handover recebendo { code: 'XXXX' } autenticado com o JWT do restaurante.
  • 4. Validar o código em tempo constante (evitando Timing Attacks); Se incorreto, decrementar contador em Redis e retornar HTTP 422 Unprocessable Entity.
  • 5. Após 3 erros, disparar evento 'KDS_HANDOVER_SECURITY_ALERT' via WebSocket para a mesa de operações.
Cenário de Teste de Aceitação Automatizado (Cucumber BDD / Gherkin):
Funcionalidade: Validação de Código de Retirada do Entregador Cenário: Coleta legítima com código correto Dado que o pedido 1042 está pronto no balcão do restaurante com status 'Pronto para Retirada' E o código gerado no aplicativo do cliente é '8492' Quando o entregador informa o código '8492' no balcão e o expedidor digita no KDS Então o sistema deve transicionar o pedido para o status 'Em Transporte' E disparar evento WebSocket para o cliente com a localização do motoboy Cenário: Tentativa de coleta com código incorreto (Tentativa de Fraude) Dado que um indivíduo informa o código incorreto '1111' para o pedido 1042 Quando o expedidor submete a validação no painel KDS Então o sistema deve rejeitar a liberação com status HTTP 422 e alerta 'CÓDIGO DIVERGENTE' E registrar log estruturado de segurança com ID do restaurante e timestamp
✓ Definition of Done (DoD na Esteira CI/CD): Teste BDD automatizado no pipeline GitLab CI; SAST Semgrep checando uso de CSPRNG ao invés de Math.random().
SR-002 Recálculo Autônomo e Integridade Criptográfica do Carrinho no Checkout (Anti-Price Tampering)
Crítica MVP (Sprint 1)
ASVS: V5.1 (Nível 3 - Business Logic Security) • OWASP: A04:2021 • ISO 27001: A.14.1.3 (Protecting Application Services Transactions) • LGPD: Princípio da Segurança e Confiança • Ameaça: THREAT-XF-02
História de Usuário Ágil (INVEST): "Como Analista de Prevenção a Fraudes, Quero que o backend recalcule autonomamente todos os valores, taxas e complementos no checkout, Para garantir que nenhum usuário adultere o valor do prato pagando centavos por pedidos caros."
Especificação Normativa (SHALL / MUST): O serviço de Checkout DEVE (SHALL) ignorar integralmente quaisquer campos de valor monetário (price, subtotal, delivery_fee, total) enviados pelo frontend ou mobile. O backend DEVE recalcular atomicamente o valor de cada item consultando o catálogo do restaurante no banco de dados e computar a taxa de entrega via Google Maps API. Se houver divergência, a transação DEVE ser imediatamente cancelada e logada.
🛠️ Passos Práticos de Implementação para a Fábrica de Software:
  • 1. Definir o DTO de Checkout recebendo estritamente IDs e quantidades: { restaurant_id: int, items: [ { item_id: int, quantity: int, option_ids: [int] } ], address_id: int }.
  • 2. Executar consulta de preços dentro de transação de leitura isolada (Read Committed) no banco PostgreSQL.
  • 3. Consultar a API de Geolocalização (Google Maps) server-to-server para obter a distância real em metros e aplicar a tabela de frete da Empresa X.
  • 4. Somar subtotal + frete - cupom_validado_server_side e montar o payload de pagamento para o Gateway.
  • 5. Bloquear o processamento se o valor recalculado diferir do valor informado na UI com log de alerta de fraude.
Cenário de Teste de Aceitação Automatizado (Cucumber BDD / Gherkin):
Funcionalidade: Integridade de Valores no Checkout Cenário: Cliente tenta adulterar o preço do item via interceptação de requisição Dado que o item 'Hambúrguer Artesanal' custa oficialmente R$ 42,00 no cardápio Quando o cliente envia um payload de checkout contendo o campo 'price: 0.01' Então o backend deve descartar qualquer valor monetário enviado pelo cliente E processar a autorização de pagamento no gateway pelo valor oficial recalculado de R$ 42,00 E registrar alerta no SIEM com o IP e token da sessão do usuário
✓ Definition of Done (DoD na Esteira CI/CD): Teste BDD automatizado com injeção de payload adulterado; DAST OWASP ZAP testando manipulação de parâmetros.
SR-003 Autenticação e Não-Repúdio de Webhooks de Liquidação Financeira (HMAC-SHA256 Pix)
Crítica MVP (Sprint 1)
ASVS: V3.2 (Nível 3 - Cryptographic Verification) • OWASP: A07:2021 • ISO 27001: A.10.1.2 (Key Management) & A.13.1.1 (Network Controls) • LGPD: Conformidade Financeira BACEN • Ameaça: THREAT-XF-03
História de Usuário Ágil (INVEST): "Como Desenvolvedor de Meios de Pagamento, Quero validar a assinatura criptográfica de cada webhook recebido do gateway Pix, Para impedir que atacantes simulem pagamentos falsos e forcem a cozinha a produzir refeições sem crédito bancário."
Especificação Normativa (SHALL / MUST): Todo webhook de liquidação financeira recebido DEVE (SHALL) conter a assinatura criptográfica HMAC-SHA256 no header 'X-Signature-SHA256'. A chave secreta (HMAC Secret) DEVE ser armazenada em cofre seguro de chaves (AWS Secrets Manager ou Vault) e rotacionada a cada 90 dias. Requisições com assinatura ausente ou divergente DEVEM retornar HTTP 401 Unauthorized sem processamento na base de dados.
🛠️ Passos Práticos de Implementação para a Fábrica de Software:
  • 1. Implementar Middleware de Inspecção de Webhook que captura o raw body (bytes originais) antes do parsing JSON.
  • 2. Recuperar a secret key do cofre de credenciais e computar hmac.new(secret_bytes, raw_body, hashlib.sha256).hexdigest().
  • 3. Comparar a assinatura computada com o header 'X-Signature-SHA256' utilizando hmac.compare_digest() para evitar ataques de temporização.
  • 4. Armazenar o campo 'idempotency_key' / 'end_to_end_id' do Pix em cache distribuído (Redis) por 24 horas para evitar Webhook Replay Attacks.
  • 5. Se o webhook já foi processado anteriormente, retornar HTTP 200 imediatamente sem duplicar a notificação para a cozinha.
Cenário de Teste de Aceitação Automatizado (Cucumber BDD / Gherkin):
Funcionalidade: Validação Criptográfica de Webhooks Pix Cenário: Webhook legítimo enviado pela instituição financeira Dado que o gateway financeiro envia notificação de liquidação do pedido 1042 E o header 'X-Signature-SHA256' contém a assinatura válida calculada com a chave secreta Quando o webhook é recebido no endpoint /api/v1/webhooks/pix Então o pedido é promovido para 'Pago' E o timer de 5 minutos do KDS do restaurante é iniciado (RN09) Cenário: Webhook forjado por atacante sem assinatura válida Dado que uma chamada externa é recebida no endpoint /api/v1/webhooks/pix Com assinatura HMAC ausente ou divergente Quando a middleware de autenticação inspeciona o pacote Então o sistema deve rejeitar imediatamente com status HTTP 401 Unauthorized E o pedido deve permanecer no status 'Aguardando Pagamento'
✓ Definition of Done (DoD na Esteira CI/CD): Teste unitário de criptografia checando rejeição de assinaturas adulteradas; Teste de carga com replay attack.
SR-004 Anonimização de PII e Mascaramento Efêmero de Geolocalização (LGPD Art. 46)
Alta Fase 1 (Sprint 2)
ASVS: V8.1 (Nível 2 - Data Protection and Privacy) • OWASP: A01:2021 • ISO 27001: A.8.24 (Use of Cryptography) & A.8.11 (Data Masking) • LGPD: Art. 46 (Medidas de Segurança) & Art. 6º, III (Minimização) • Ameaça: THREAT-XF-04
História de Usuário Ágil (INVEST): "Como Cliente da Plataforma, Quero que meu número de telefone pessoal e sobrenome nunca sejam expostos ao entregador, Para preservar minha privacidade e segurança física antes, durante e após a entrega."
Especificação Normativa (SHALL / MUST): A API de entregas DEVE (SHALL) expurgar sobrenome, CPF e número telefônico real do cliente de todos os payloads entregues ao aplicativo do motoboy. O contato telefônico entre as partes DEVE operar obrigatoriamente através de gateway VoIP/PSTN com chamada mascarada. O endereço de entrega DEVE ser removido do cache local do dispositivo do entregador imediatamente após a confirmação da entrega.
🛠️ Passos Práticos de Implementação para a Fábrica de Software:
  • 1. Criar Serializer / DTO específico para a persona Entregador (DriverOrderDTO) que projeta apenas { first_name: 'Maria', address: 'Rua X, 123', delivery_notes: 'Apartamento 302' }.
  • 2. Integrar com provedor de telefonia mascarada (Twilio / Zenvia / TotalVoice) gerando um número virtual temporário válido por 60 minutos.
  • 3. Configurar diretiva no app mobile do entregador para limpar o SQLite / Realm local ao receber evento 'ORDER_COMPLETED'.
  • 4. Criptografar as coordenadas GPS em trânsito com TLS 1.3 e em repouso com AES-256 no banco de dados.
  • 5. Criar job diário de anonimização que expurga logs de geolocalização bruta após 30 dias da conclusão do pedido.
Cenário de Teste de Aceitação Automatizado (Cucumber BDD / Gherkin):
Funcionalidade: Mascaramento de Dados Pessoais do Cliente Cenário: Entregador consulta dados do pedido em trânsito Dado que o pedido 1042 está em rota de entrega com o motoboy Quando o entregador acessa os detalhes do cliente no aplicativo Então ele deve visualizar apenas o primeiro nome 'Maria S.' e o endereço de destino E o CPF e número real de telefone não devem constar no payload HTTP da resposta E o acionamento de ligação deve disparar o proxy de voz sem revelar o número real
✓ Definition of Done (DoD na Esteira CI/CD): Regra DAST/SAST que analisa schemas JSON garantindo que campos sensíveis não vazem para endpoints mobile de parceiros.
SR-005 Isolamento Multi-Tenant Estrito em Nível de Linha (RLS) para o Painel KDS de Cozinha
Crítica MVP (Sprint 1)
ASVS: V4.1 (Nível 3 - Access Control Architecture) • OWASP: A01:2021 • ISO 27001: A.9.4.1 (Information Access Restriction) • LGPD: Segredo Industrial & Proteção de Negócio • Ameaça: THREAT-XF-05
História de Usuário Ágil (INVEST): "Como Restaurante Parceiro, Quero ter a certeza de que nenhum outro restaurante visualize meus pedidos, faturamento ou clientes no painel KDS, Para garantir o sigilo das minhas vendas e das minhas operações."
Especificação Normativa (SHALL / MUST): Todas as consultas e subscrições WebSockets do painel KDS DEVEM (SHALL) aplicar cláusula de isolamento multi-tenant forçada. O banco de dados PostgreSQL DEVE ter Row-Level Security (RLS) habilitado na tabela de pedidos, filtrando por restaurant_id extraído do claim verificado do token JWT da sessão, impedindo acesso cruzado mesmo em caso de erro na camada de aplicação.
🛠️ Passos Práticos de Implementação para a Fábrica de Software:
  • 1. Habilitar RLS no PostgreSQL: ALTER TABLE orders ENABLE ROW LEVEL SECURITY;.
  • 2. Criar política de isolamento: CREATE POLICY kds_tenant_isolation ON orders USING (restaurant_id = current_setting('app.current_restaurant_id')::int);.
  • 3. Na camada de conexão (pool de banco), injetar a variável de sessão antes de cada query: SET LOCAL app.current_restaurant_id = :authenticated_restaurant_id.
  • 4. No broker de WebSockets (Redis PubSub), estruturar os tópicos estritamente como /kds/restaurants/{restaurant_id}/orders.
  • 5. Validar autorização no handshake do WebSocket rejeitando conexões com HTTP 403 se o JWT não pertencer àquele restaurante.
Cenário de Teste de Aceitação Automatizado (Cucumber BDD / Gherkin):
Funcionalidade: Isolamento Multi-Tenant no Painel KDS de Cozinha Cenário: Restaurante A tenta consultar pedidos do Restaurante B via API Dado que o operador autenticado pertence ao Restaurante A com ID 501 Quando ele envia requisição GET para /api/v1/kds/orders/1043 (pertencente ao Restaurante B com ID 502) Então o sistema deve bloquear o acesso retornando código HTTP 403 Forbidden E a resposta não deve revelar nenhum dado do pedido pertencente ao competidor
✓ Definition of Done (DoD na Esteira CI/CD): Testes automatizados de penetração (BOLA Testing Suite) simulando tentativa de acesso cruzado com tokens distintos.
